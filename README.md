# TASK-REPORT Protocol

**机器可读 / 人可读分离的两层 Agent 协作协议**

让"干活的 Agent"只说机器语言，让"汇报的 Agent"专门翻译成人话。零代码、零依赖，复制粘贴即可串联任意 AI 平台的分散算力。

---

## 痛点

### 1. 免费 Token 额度被浪费在"说人话"上

各大 AI 厂商为了留存用户，持续赠送免费 token 额度（如智谱 5 亿 token 礼包）。但一个现实问题随之而来：

> 同一个 Agent 既要干活，又要输出人类可读的汇报。于是大量 token 被消耗在"描述过程、表达情绪、自我解释"上——真正的任务产出只占输出的一小部分。

更糟的是，这些输出往往是一长串夹杂过程与结论的对话，人类根本读不完，只能截取片段使用。

### 2. 平台生态互不互通，算力只能靠人肉聚合

每个厂商的额度都绑定在自家平台内，模型智力也参差不齐。跨平台协作没有原生通道：

- A 平台的额度不能给 B 平台用
- 任务中途换平台，上下文全部丢失
- 想用多家额度并行推进一个复杂任务，只能人工搬运信息

### 3. 单一模型的智力天花板限制任务完成度

复杂任务往往需要多个模型各司其职（一个擅长检索、一个擅长规划、一个擅长总结）。但现有框架把"规划 + 执行 + 汇报"压在同一个模型上，能力被稀释，任务完成度打折。

### 4. 强行让机器说人话 = 双重损失

如果要求执行 Agent 输出人类友好语言，就会产生双重浪费：既损失了产出信息的密度，又增加了翻译所需的 token 开销。

---

## 解决思路

把任务拆成两层，让每个 Agent 只服务一个受众：

```
┌─────────────┐      复制粘贴      ┌─────────────┐
│   执行 Agent  │ ───────────────▶ │   汇报 Agent  │
│   （工头）     │    TASK-REPORT    │   （经理）     │
│              │                   │              │
│ 只输出机器语言  │                   │ 只翻译成大白话 │
│ token 全花在  │                   │ token 全花在  │
│   干活上      │                   │   汇报上      │
└─────────────┘                   └─────────────┘
         ▲                                │
         └──────── 人肉总线：你来粘贴 ──────┘
```

- **执行 Agent（工头）**：只干活，输出固定格式的机器可读报告（TASK-REPORT），不面向人类可读性做任何整理，token 100% 花在产出上。
- **汇报 Agent（经理）**：只消费执行 Agent 的报告，翻译成不懂技术的老板能听懂的大白话，并顺带给出执行质量的评审判断。
- **人肉总线**：你手动复制粘贴两份对话之间的纸条。这是冗余的，但也是最强的——**不需要任何框架、任何 API、任何部署**，任何支持多对话的 AI 平台都能跑。

---

## 解决的问题

| 痛点 | 解决方式 |
|------|----------|
| Token 浪费在说人话上 | 执行层不再输出人类友好文本，token 全用于任务产出 |
| 输出太长、人类读不完 | 汇报层只输出简洁大白话，老板 30 秒读完 |
| 平台生态互不互通 | 人肉总线 + 固定协议，任意平台之间搬运上下文 |
| 单模型智力天花板 | 每层可选用不同平台/不同模型，各司其职 |
| 机器说人话的双重损失 | 两层分离，每层只服务一个受众（机器 or 人） |
| 跨轮次状态丢失 | TASK-REPORT 携带回合数、状态码、下一步动作 |

## 协议规范

### 格式定义

```
[TASK-REPORT v1]
回合: N/M
目标: <一句话目标>
动作: [<工具/操作1>] → [结果摘要]
结果: <关键产出>
状态: ON_TRACK | AT_RISK | BLOCKED | DONE
下一步: <下一步动作或"无">
风险: <风险描述或"无">
```

### 状态码含义

| 状态码 | 含义 | 经理汇报策略 |
|--------|------|-------------|
| `ON_TRACK` | 按计划推进 | "一切正常，继续往下走" |
| `AT_RISK` | 有潜在问题但能解决 | "目前没问题，但有 X 处需要注意" |
| `BLOCKED` | 被卡住了 | "遇到障碍，原因是 X，需要你帮忙 Y" |
| `DONE` | 任务完成 | "所有环节已完成，最终产出是 XXX" |

### 示例

```text
[TASK-REPORT v1]
回合: 2/3
目标: 提取各文件金额字段
动作: [read_file f1] → 成功提取金额 ¥12,800
      [read_file f2] → 成功提取金额 ¥8,500
      [read_file f3] → 失败，文件格式损坏
      [retry read_file f3] → 成功提取金额 ¥15,200
结果:
  - f1: ¥12,800
  - f2: ¥8,500
  - f3: ¥15,200
状态: AT_RISK
下一步: 继续提取 f4 和 f5
风险: f3 曾损坏，后续文件可能也有类似问题
```

## 使用流程

```
你 → 开对话A → 粘贴【工头提示词】→ 发任务指令
工头干活 → 输出 [TASK-REPORT v1] ...
你复制这段 → 开对话B → 粘贴【经理提示词】→ 粘贴工头纸条
经理翻译 → 大白话汇报给你
```

配套模板：

- `task_report_worker_prompt.md` — 工头提示词（执行 Agent）
- `task_report_manager_prompt.md` — 经理提示词（汇报 Agent）

## Token 效率分析

### 为什么结构化输入省 Token

模型训练数据中包含海量 API 日志、JSON 响应、命令行输出。输入 `[TASK-REPORT v1]` 这种固定格式时，模型走的是**模式匹配路径**而不是逐字解析路径——识别到 `回合: 2/4` 就知道是进度标记，推理成本接近读取字符本身。

### 单 Agent vs 双 Agent 对比

| 维度 | 单 Agent（干活 + 说人话） | 双 Agent（本协议） |
|------|--------------------------|-------------------|
| Token 分配 | 分散在干活 + 描述过程 + 自我解释 | 工头 100% 产出，经理 100% 汇报 |
| 输出长度 | 长串对话，人类读不完 | 工头短而密，经理简洁清晰 |
| 可移植性 | 绑定单个平台 | 任何支持多对话的平台都能跑 |
| 容错性 | 一个模型挂了全停 | 可以换平台接力，上下文不丢 |

## 适用场景

- 消耗各平台赠送的免费 token 额度
- 需要跨平台协作的任务
- 对输出可读性要求高、但对过程细节不关心的场景
- 想降低单次对话阅读成本的场景

## 不适用场景

- 需要实时交互的场景（复制粘贴有延迟）
- 需要精确控制每一步的场景（人肉总线不够精细）
- 单 Agent 就能高效完成的简单任务
